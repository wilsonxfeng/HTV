# Ask ReMotion integration

Ask ReMotion is integrated into the Progress tab. No new packages or database migrations are needed. See [the recording and demo plan](PROGRESS_DEMO_PLAN.md).

## Public integration points

- `POST /api/ask-remotion`, registered in `server/app.ts`. Existing bearer authentication and assigned-patient authorization (patient and clinician roles) run before interpretation or database access. Selected `patientId` is validated against the authenticated principal, never generated by Gemini.
- `src/features/ask-remotion/AskRemotionPanel.tsx`: scoped cream/sage panel, used in Progress and kept mounted above Movement Echoes. Patient, exercise and side changes abort outstanding work; newer queries supersede older responses.
- `EvidenceFocus` in `src/features/ask-remotion/contracts.ts`: `{sessionId, repetitionIndex, timestampMs, token}`. `MovementEchoes.evidenceFocus` selects an already authorized session/repetition. `EchoViewer` seeks the original video clock and pauses after metadata loads. No timestamp means a session-level result, opening at the beginning with an explicit unavailable notice. Never infer a timestamp from a date.
- Progress `openEvidence` loads detail/video through existing authorized repository methods. Single recordings use `toEchoSession`; comparisons reuse `fetchEchoSessions`. Abort signals propagate through both paths. Previously loaded recordings, overlay enablement, opacity and ghost choices remain mounted while searching. New provided sessions are added through the small controlled input hook in Movement Echoes.

Example request:

```json
{
  "patientId": "AUTHORIZED-PATIENT-UUID",
  "question": "Which session had the greatest recorded finger opening?",
  "exerciseContext": {"exerciseId":"finger-spread-close","side":"Right"}
}
```

An optional validated `preset` (`greatest-finger`, `first-latest-finger`, `smallest-knee`) executes the same database executor with a predefined intent, independently of Gemini availability. The response labels `source: preset`; it does not pretend Gemini ran.

## Interpretation and evidence

`server/features/ask-remotion/intentParser.ts` uses the existing `@google/genai` dependency and server configuration. Gemini receives only the question, selected exercise/side and whitelisted catalog, never database rows, patient identifiers, videos or credentials. Structured JSON is checked by a strict Zod schema, including aggregation compatibility. Unknown fields, metrics and invalid JSON are rejected. Provider failure returns a safe 503 with suggested-search guidance.

Intents: `find_extreme` (`min`/`max`), `compare_sessions` (first/latest), `find_recent` (`first`/`latest`), `unsupported`. No arbitrary SQL, medical chat, diagnosis or recovery assessment. Ambiguous questions should produce `unsupported` and a clarification message.

Metrics, all in camera-estimated degrees:

| Key | Definition and timestamp |
| --- | --- |
| `finger_opening` | Mean index–middle, middle–ring, ring–pinky separation at a valid detected repetition peak; stored `peak_ms` is already video time. Static poses excluded. First/latest compares each session's greatest valid repetition peak. |
| `finger_thumb_index`, `finger_index_middle`, `finger_middle_ring`, `finger_ring_pinky` | Stored `pairs[].achieved` hold-angle session aggregates. No exact timestamp supplied. |
| `knee_range` | Stored `body.movementRange`, not maximum knee angle. Session aggregate; no timestamp. |
| `knee_peak` | Stored `body.maximumAngle`. Session aggregate; no timestamp. |
| `elbow_range` | Stored `body.movementRange` for unweighted bicep curl. Session aggregate; no timestamp. |

Experimental trunk rotation is deliberately unsupported: current code does not expose validated rotation degrees.

`queryExecutor.ts` uses the existing `Database` abstraction: parameterized PostgreSQL query on `sessions`, `session_reports`, `repetitions`, always filtered by patient, exact exercise, side and completed status. It works with the existing TigerData/pg connection and embedded PostgreSQL test/demo database. The model cannot supply table names or SQL fragments.

Candidates require at least 80% session tracking; finger peaks also require valid repetitions and at least 80% repetition coverage. Missing/nonfinite metrics are excluded. Compatibility anchors to the latest eligible metric-bearing session: exercise/side, camera view, analysis version, video orientation, demonstration/video kind and tracking mode; finger metrics additionally require identical neutral/target/source calibration. Calibration creation date and recording duration do not prevent comparison. Different cohorts are never silently pooled. Dates/IDs provide deterministic tie ordering. Fewer than two comparable sessions produces an empty comparison.

Evidence includes actual session/date, metric/value/unit, quality, repetition index, nullable timestamp and video availability. No Gemini-generated numbers or narrative. Video keys/URLs are absent from search responses; existing signed-video endpoints handle playback.

## Configuration and setup

Use existing `.env.server.example` / `server/README.md`:

- `GEMINI_API_KEY` and `GEMINI_MODEL`: server-side only. Existing model configuration is reused; choose a model available to your account. The Progress migration verification below includes a typed Gemini question against existing cloud demo history.
- Existing `DATABASE_URL`, verified database TLS, `AUTH_SECRET`, S3/R2 settings and `APP_ORIGIN`, `API_PORT` apply unchanged.
- Frontend uses existing `VITE_API_BASE_URL`, or Vite's existing `/api` proxy to port 3001. No client-side AI key.
- Cloud: `npm run api:dev` and `npm run dev`; connect a patient token authorized for the participant with completed uploads.
- Local fictional demo: `npm run api:demo:seed` (existing seed requires ffmpeg), then `npm run dev` and open Progress and connect local demo access. Presets work without a Gemini key. The local hand/knee overlay buttons are separate from this authenticated search; record and sync actual sessions for searchable demo evidence.

## Current integration

`src/components/Progress.tsx` owns the search panel, authorized recording loading, exercise/side filters, comparable reference groups, trends and overlay navigation. Connection and consent controls live in `src/features/clinical-data/components`. The former clinician dashboard, standalone HTML entry and separate build command have been removed. Server role checks still restrict uploads to assigned patient access; search permits both assigned roles and continues rejecting cross-patient access.

Search remains mounted above the viewer. Source, account, exercise and side changes cancel pending operations and clear loaded evidence. Remote extracted images remain in memory; the explicit local demo viewers may use prepared caches. An upload finishing while Progress is open refreshes its history.

## Verification and limits

Automated checks: full Vitest suite (141 tests across 24 files passed); backend TypeScript check; production app, clinician, Movement Echoes and voice builds. Tests cover real stored-data max/min/comparison, changed-data answers, patient authorization, quality/version filters, exact session/rep/timestamp, no data, strict mocked Gemini output, provider failure, stale responses and video seek/pause/continued play. Existing feature tests also run.

Real Chromium verification used an isolated in-memory API and the repository's existing team knee footage/pose data, completed through the existing upload/completion path: knee-range preset returned 51.9°, opened the actual video at 0 seconds paused, explicitly reported no exact timestamp; missing finger history and unconfigured Gemini showed their real errors. No page exceptions. No personal browser profile or clinical database was used.

Not verified: live Gemini/account model availability, remote TigerData/R2 connectivity, ElevenLabs live audio, remote deployment, visual ghost extraction quality across every recording. Browser precision for a finger peak is covered by a direct media-element regression test rather than a new end-to-end finger recording. Voice build retains its existing large-chunk warning. This is a prototype using the existing access-token model, not a claim of production medical compliance.

Limits: first/latest stays within the latest eligible configuration; current SQL fetches authorized exercise history then chooses deterministic evidence in application code, suitable for MVP but should use indexed/limited SQL aggregation for very large histories. Count/week and low-quality searches are not implemented. Out-of-catalog intent returns unsupported. Suggested searches provide reproducible fallback; they do not synthesize measurements. Prepared video/masks can take time to load; loading states reflect actual work.
